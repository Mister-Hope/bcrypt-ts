# CLAUDE.md

This file provides AI coding assistants (GitHub Copilot, Claude Code, etc.) with a project overview, architecture notes, development conventions, and known issues for this repository (bcrypt-ts), so that relevant context is established before modifying code.

## Project overview

bcrypt-ts is a pure TypeScript implementation of the bcrypt password hashing function with zero runtime dependencies. It is hash-format compatible with the C++ [bcrypt](https://npmjs.org/package/bcrypt) binding on Node.js and also runs in the browser. It is derived from dcodeIO/bcrypt.js (whose copyright and Apache-2.0 license notice are preserved in the source); this project is released under MIT. Current version: v9.0.1. Selling points over bcrypt.js: fully written in TypeScript, separate ESM bundles for Node and browser, minified builds, and better tree-shaking. Note the inherent properties of the bcrypt algorithm: the pure JS implementation is ~30% slower than the C++ binding, the input limit is 72 bytes (mind multi-byte UTF-8 characters), and hashes are fixed at 60 characters (`$2b$` format).

## Architecture & modules

The entry `src/index.ts` only re-exports; the public API consists of `hash`/`hashSync`, `compare`/`compareSync`, `genSalt`/`genSaltSync`, `getRounds`, `getSalt`, and `truncates`. Core module responsibilities: `src/crypt.ts` is the Blowfish encryption core (`encipher` uses a manually unrolled loop for performance; `key` and `expensiveKeyScheduleBlowFish` do the key schedule); in async mode it splits work into chunks of `MAX_EXECUTION_TIME = 100ms`, and after each chunk it uses `nextTick` to place the next chunk at the end of the event queue, yielding the main thread. `src/hash.ts`'s `hashString` parses the salt (supports the four prefixes `$2$`, `$2a$`, `$2b$`, `$2y$`), validates that rounds are in 4-31, and assembles the final hash string. `src/salt.ts` generates `$2b$`-prefixed salts and silently clamps rounds to [4,31]. `src/base64.ts` implements base64 encode/decode with the custom bcrypt alphabet. `src/uft8.ts` computes UTF-8 byte lengths and byte conversion (used for the 72-byte truncation check). `src/helpers.ts` provides `getRounds`/`getSalt`/`truncates`. `src/constant.ts` holds the Blowfish P-array, S-boxes, C initial values, and the base64 lookup tables (all original upstream values — never modify).

## Dual-environment build (important convention)

The project builds two bundles (`node` and `browser`) via `tsdown.config.ts`. The only code difference between them is how two "platform-agnostic" modules are resolved: `src/random/` (randomness source: node uses `globalThis.crypto.getRandomValues`; browser uses Web Crypto and throws when no secure random source is available) and `src/nextTick/` (node uses `setImmediate` and falls back to `setTimeout` on edge runtimes; browser prefers `scheduler.postTask`, otherwise `setTimeout`). These bare module names (`random`, `nextTick`) are rewritten per platform via tsdown's `alias`; their types are declared in `src/shims.d.ts` with `declare module`. `vitest.config.ts` configures the same aliases so tests always use the node implementation. Any change to platform-related logic must update both node and browser implementations and keep `shims.d.ts` and the alias configs in sync. Since v8.0.0 the CJS/UMD outputs were removed; only the ESM `dist/node.js` and `dist/browser.js` are produced (with dts and sourcemap).

## Test conventions

Tests live in `__tests__/` with 8 spec files and currently 63 cases; line/branch/function/statement coverage is 100%, and new code must keep it at 100% (enforced by the CI cobertura report). Tests import the node implementation from `src/` directly through vitest aliases (note the `.js` suffix in import paths — that is ESM style, and vitest resolves it to the `.ts` files). `progress.spec.ts` covers the async progress callback; `nextTick.spec.ts` covers the node implementation; the bench files (`hash.bench.ts`, `compare.bench.ts`) use vitest bench for performance measurement and are not a test gate.

## Known issues & notes

- **`$2$`-prefixed hashes cannot be verified by this library itself (open)**: `hash`/`hashSync` explicitly support `$2$` (no minor revision) salts and produce 59-character hashes, but `compare`/`compareSync` have an early `hash.length !== 60` return, so such hashes always compare false (`getSalt` also rejects them via its length check). This matches upstream bcrypt.js (inherited for compatibility) and `$2$` is deprecated, but it is an internal self-consistency gap; changing it requires careful compatibility review. Default generation and verification go through `$2b$` and are unaffected.
- **`decodeBase64` c4 validation (fixed — intentional divergence from upstream)**: when the 4th character of a group is invalid (lookup returns -1), decoding now `break`s like it does for c1/c2/c3, instead of emitting a corrupted byte (65535). Before the fix, an invalid character at positions 3/7/11/15/19 of a 22-character salt (the c4 position of each group) still yielded exactly 16 decoded bytes that passed the length check, so `hashSync` silently accepted a bad salt and produced a hash instead of throwing "Illegal salt". This is an **intentional divergence** from upstream bcrypt.js, which still silently emits the corrupted byte. Tests: see the c4 cases in `base64.spec.ts` and `hash.spec.ts`.
- **Boundary behavior**: `genSaltSync`/`genSalt` silently clamp rounds to [4,31] (e.g. passing 3 yields `$04$`), while `hashString` throws for explicitly out-of-range rounds in a salt string — the inconsistency matches bcrypt.js.
- **Async API style**: `compare`/`genSalt` use `new Promise` with manual resolve/reject (combined with `nextTick`), not async/await — keep this style when modifying.
- `src/constant.ts`'s P/S/C arrays and base64 tables are the root of algorithm correctness; any "optimization" must first be cross-validated against upstream, and the known-vector tests (e.g. base64 encode/decode) must keep passing.
